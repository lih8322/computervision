# 표면 결함 검출 — ECC 정렬 + 적응형 임계값 (v3)

## 개요

[v2 (adaptive)](../AnomalyDetection-adaptive) 는 픽셀별 Z-score로 판정했지만, k를 올려도 과검이 34.8 %에서 멈췄습니다. 이 부분이 무늬가 아니라 입력–기준의 미세한 위치·회전 어긋남(정렬 오차) 때문일 수 있다고 보고, v3에서는 차분 전에 입력을 기준에 맞추는 정렬 단계를 추가해 봤습니다.

밝기 기반 정합인 ECC(`cv::findTransformECC`, 아핀)를 사용합니다. 속도·안정성을 위해 1/4로 축소한 영상에서 변환을 추정하고, 이동 성분만 배율로 되돌려 원본에 적용합니다(전체 해상도 대비 ~447 ms → ~52 ms, 정확도는 비슷).

## 파이프라인

v2와 같되 차분 전에 정렬이 들어갑니다.

```
detect: 입력 → 전처리
   → ★ ECC 정렬: 입력을 기준(mean)에 warp (1/4 축소로 추정, 실패 시 원본 폴백)
   → Z-score = |정렬된 입력 − mean| / max(σ, sigma_min)   (v2와 동일)
   → 블러 → 이진화(>k) → 모폴로지 → 연결요소
```

`use_ecc=0` 인자로 정렬을 꺼서 v2와 같은 조건으로 비교할 수 있습니다.

## 결과

MVTec AD capsule · 정상 219장 학습 → test 132장(정상 23 / 결함 109) · Intel i5-6600, Release x64.

**실험 E — k 스윕, 정렬 on/off 비교** ([`experiments/exp_E_ecc_vs_noecc.csv`](experiments/exp_E_ecc_vs_noecc.csv))

같은 미검 수준끼리 비교했을 때:

| 미검 ≈ | 정렬 OFF 과검 | 정렬 ON 과검 | 차이 |
|---|---:|---:|---:|
| ~2–3 % | 82.6 % (k=2.5) | **73.9 % (k=2.5)** | −8.7 %p |
| ~6 % | 65.2 % (k=3.5) | 65.2 % (k=3.0) | 0 |
| ~10–13 % | 56.5 % (k=4.0) | 60.9 % (k=3.5) | +4.4 %p |
| ~32–37 % | 34.8 % (k=5.0) | 34.8 % (k=5.0) | 0 |

정렬은 엄격한 임계(낮은 미검) 구간에서만 과검을 낮췄고(k=2.5에서 −8.7 %p), 중간 구간에서는 차이가 없거나 오히려 나빠졌습니다. **과검 34.8 %는 정렬로도 내려가지 않았습니다.**

### 해석

정렬 오차가 과검의 일부 원인은 맞지만(엄격 구간의 개선이 그 근거), 주원인은 아닌 것으로 보입니다. 남은 34.8 %는 정렬로도 σ로도 걸러지지 않아, 알고리즘보다 **조명·촬영 조건** 쪽에 원인이 있을 가능성이 큽니다.

이 34.8 %는 **단일 골든 이미지 차분 방식의 구조적 한계**를 보여주는 값이며, 실무에서는 이 지점부터 광학 조건 개선 또는 학습 기반(딥러닝) 방법이 병행됩니다. 즉 검사 방법마다 촬영 통제에 대한 의존도가 다르며(차분 > 특징 기반 > 학습 기반), 환경에 맞춰 방법을 선택하게 됩니다.

**비용:** 정렬(축소 ECC)이 프레임마다 더해져 처리시간이 **~22 ms → ~52 ms** 로 늘었습니다.

정리하면, v1(고정)→v2(적응형)→v3(정렬)을 거치며 소프트웨어 처리만으로는 남는 한계가 있고, 그 지점부터는 촬영 조건 통제가 필요하다는 것을 실험으로 확인했습니다.

## 빌드 · 실행

Visual Studio 2022, vcpkg OpenCV(x64, `video` 모듈 포함), **Release · x64**.
```
AnomalyDetection-registration.exe <capsule_root> [k] [sigma_min] [min_area] [blur_ksize] [morph_ksize] [use_ecc]
  기본값: k=3.0  sigma_min=3.0  min_area=50  blur_ksize=5  morph_ksize=5  use_ecc=1
  use_ecc=0 → 정렬 끄기(= v2와 동일 조건)
```
